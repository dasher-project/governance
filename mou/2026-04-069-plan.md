# Dasher v6 — Project Plan (Annex I to the MoU)

**Grant:** 2026-04-069 (NGI0 Commons Fund, April 2026 call)
**Project:** Dasher v6 — cross-platform, accessible continuous-gesture text entry
**Planned start:** October 2026
**Total budget:** €50,000

All work takes place in public in the [dasher-project](https://github.com/dasher-project) GitHub organisation. Tasks are executable in any order unless a dependency is stated; the plan can be modified in agreement with NLnet as the project evolves. Every task in this plan is a research and development activity — engineering, specification, bug fixing, evaluation or documentation.

**Owner initials:** WW (Will Wade, UK, project lead and point of contact), KM (Kirsty McNaught, UK, developer), UX (UX/design contributor, to be recruited), ANY (open to additional listed contributors). Owner assignment is flexible and coordinated with the lead; in this public document amounts attach to milestones, not to people.

---

## 1. Onboarding and first-run experience overhaul

Dasher's main adoption barrier, identified repeatedly in the project scope document, is that it is "a problematic interface to understand without training". This task delivers the design overhaul promised in the application and announced to the user community: user research with new and existing Dasher users, wireframes, a start-up guide, a settings user-experience overhaul, and a graduated onboarding flow — introducing settings and control gradually as a user becomes proficient. Design work is captured in `dasher-design-guide` and implemented first in `dasher-web`, where iteration is fastest. UI strings and shared assets flow through `dasher-shared-resources` so all frontends present one consistent onboarding experience.

Suggested owners: UX, WW

Milestone(s):
a. User research round with new and existing Dasher users; findings and wireframes published in `dasher-design-guide` — €1,200
b. Start-up guide and graduated onboarding flow prototyped and implemented in `dasher-web` — €1,500
c. Settings user experience overhauled so the most-used options are discoverable and the rest progressively revealed — €1,300
d. Learning mode (replacing the legacy "game mode") teaching continuous-gesture input step by step — €1,000

Amount: €5,000

## 2. Accessibility design squads

Beyond first-run UX, the application calls for iterative, user-led design across the whole feature set. This task runs time-boxed "design squads" — small, focused cycles pairing the UX contributor with groups of users of a specific access method (switch users, eye-gaze and head-mouse users, and low-vision/auditory-feedback users). Each cycle produces concrete design decisions and acceptance criteria that feed the relevant RFCs and the known-gaps section of the governance#41 test checklist. Outcomes are documented openly in `dasher-design-guide` so platform frontends can apply them consistently.

Suggested owners: UX, ANY

Milestone(s):
a. `dasher-design-guide` extended with per-access-method design patterns and acceptance criteria — €1,200
b. Three design-squad cycles run and documented (switch users; eye-gaze/head-mouse; low vision and auditory feedback) — €1,300
c. Accessibility audit of all frontends against the agreed criteria, findings filed as issues — €1,000

Amount: €3,500

## 3. Eye-gaze input performance

The scope document promises "a cross-platform, eye gaze, headmouse and direct accessible version of Dasher", and the user community has asked for eye-gaze to work really well. This task evaluates the current eye-gaze path end to end — pointer smoothing, zoom dynamics under continuous gaze, dwell behaviour and latency budgets — and specifies a calibration and profile workflow so a user's gaze setup survives restarts and moves between machines. Improvements land in `DasherCore` input filters (RFC 0010 canonical model) and are validated per platform against representative eye trackers.

Suggested owners: WW, KM

Milestone(s):
a. Eye-gaze input evaluation and calibration/profile specification published — €1,500
b. Tracking smoothing, zoom dynamics and latency improvements implemented in `DasherCore` input filters — €1,500
c. Per-platform eye-gaze validation with representative hardware, findings and default profiles published — €1,000

Amount: €4,000

## 4. Prediction engine: canonical model and gRPC language-model backend

The core of the application is "a new next letter and next n word prediction engine which will support a range of models in different languages". This task hardens the prediction layer in `DasherCore`: extending the RFC 0010 canonical selection model so alternative language models can be plugged in behind a stable interface, and identifying optimal settings for the gRPC language-modelling backend called for in the scope document. It includes an offline default model so Dasher works without a backend connection, plus packaging so models can be downloaded and cached per platform. Configuration discovery (which model, which backend, which latency budget) is designed so the same options work across Android, Apple, GTK, Windows, web and Electron frontends.

Suggested owners: KM, ANY

Milestone(s):
a. Pluggable language-model interface specified and implemented in `DasherCore` under RFC 0010 — €2,000
b. gRPC backend integration with offline fallback and configuration discovery documented — €2,500
c. Model packaging, download and caching across platforms — €1,500
d. Emoji support: settings-gated emoji group in the alphabet model (builds on DasherCore#99), specified and shipped — €1,000

Amount: €7,000

## 5. Phoneme and word-prediction training pipeline

The `dasherPhonemeTraining` repository contains the training tooling for Dasher's prediction models; it needs to be reproducible and documented before the grant's evaluation work (task 10) can trust its outputs. This task refactors the pipeline so models can be trained from public corpora with recorded, versioned configurations, retrains English models as the priority language, and produces initial Spanish and German models as named in the scope document. Trained models, evaluation scores and training instructions are published so third parties can build models for further languages without grant involvement.

Suggested owners: KM, ANY

Milestone(s):
a. Training pipeline reproducible end-to-end with documented configuration — €1,500
b. English models trained and evaluated; Spanish and German initial models produced — €1,500
c. Models and training documentation published — €500

Amount: €3,500

## 6. Switch access: profiles RFC and USAHP capture layer

Switch users are a core Dasher audience, and governance#43 records that the switch-access specification is still open. This task writes and drives to acceptance the switch-access profiles RFC (scanning mode, timing parameters, hardware support, saved profiles), building on the RFC 0010 filters that already implement one-switch and two-switch modes in `DasherCore`. It then implements the USAHP local switch-event broker adopted via governance#25 as the capture layer on the desktop frontends, relating to the work tracked in `alternative-switch-controls-for-dasher`. The RFC's UX decisions (scan highlighting, auditory feedback per step) come from the switch design squad in task 2.

Suggested owners: WW, ANY

Milestone(s):
a. Switch access profiles RFC written and accepted (closes governance#43) — €1,000
b. USAHP switch-event broker capture implemented in the desktop frontends (governance#25) — €2,000
c. Scanning modes, timing parameters and loadable switch profiles implemented in `DasherCore` and the frontends — €2,000

Amount: €5,000

## 7. Voice and speech output

governance#42 records that speak-on-space, speak control nodes and per-platform TTS all exist in some form but without a specification — and that speech is "the voice of the product" for users who cannot look at the screen while typing. This task writes the voice/speech output RFC (when speech fires, interruption behaviour, voice selection, rate/volume/pitch ownership, direct-mode behaviour) and then unifies the existing per-platform implementations — speech-dispatcher via `tts-wrapper` (AACTools) on GTK, SAPI on Windows, Android TTS, AVSpeechSynthesizer on Apple — behind one consistent settings surface. It also hooks speech into the phrase/communication-board integration questions raised in the issue.

Suggested owners: WW, ANY

Milestone(s):
a. Voice/speech output RFC written and accepted (closes governance#42) — €800
b. Per-platform TTS unified behind consistent configuration across all frontends — €2,200
c. Speak-on-space and speak control node options exposed in settings, with documented behaviour in direct mode — €1,000

Amount: €4,000

## 8. Cross-platform releases and continuous integration

The fragmentation of v5 across Windows, Linux, iOS and Android is the historical failure mode this project exists to fix, so regular, simultaneous releases across all v6 frontends are a deliverable in themselves. This task establishes CI builds and automated test runs in each platform repository (`Dasher-Android`, `Dasher-Apple`, `Dasher-GTK`, `Dasher-Windows`, `dasher-web`, `dasher-electron`), wired to the test matrices and pre-release checklist from governance#41. It also delivers the application's deliverable 2: on-screen keyboard integrations on iOS, Android and Windows so Dasher can output text to the operating system rather than only within the app. Tagged releases with notes land on all platforms at once.

Suggested owners: KM, ANY

Milestone(s):
a. CI pipelines and per-platform test runs green in all frontend repositories, driven by the governance#41 checklist — €1,500
b. First simultaneous tagged release across all frontends with published release notes — €1,000
c. On-screen keyboard integration (OS text output) on iOS, Android and Windows — €2,500
d. iOS and Android stabilisation: crashers and long-standing platform bugs fixed, verified against the governance#41 checklist — €1,000

Amount: €6,000

## 9. SDK and developer documentation

The application promises "a working SDK to allow developers to integrate Dasher into existing AT", with code samples in a range of languages (a React app, a C# app) and build instructions for different operating systems — enabled by the permissive licence chosen for the v6 codebase. This task defines the public SDK surface on top of `DasherCore` (embedding, input injection, prediction queries, output handling) with a versioning policy, ships working samples, and publishes developer documentation covering building for each platform. The SDK is validated by building at least one sample integration end-to-end.

Suggested owners: KM, WW

Milestone(s):
a. SDK API surface specified with versioning policy — €1,500
b. Code samples (React and C#) and per-platform build instructions published — €1,500
c. Developer documentation complete, including one validated end-to-end integration example — €1,500

Amount: €4,500

## 10. User and developer documentation (written and video)

The application's deliverable 6 is "video content alongside a website to demonstrate Dasher's features for end-users and developers"; here it is scoped as documentation and training material. This task converts legacy word-processor documentation into markdown user guides hosted on the project `website` repository, covering installation, access methods, prediction settings and the new onboarding flow. It then produces short training videos for end users (getting started, switch access, voice output) and for developers (SDK integration, building the frontends), published alongside the written guides as training documentation.

Suggested owners: WW, ANY

Milestone(s):
a. User guides published in markdown on the project website — €1,200
b. End-user training videos (getting started, switch access, speech output) published — €800
c. Developer-facing videos (SDK integration, per-platform builds) published — €1,000

Amount: €3,000

## 11. User research: empirical text-entry-rate evaluation

The application commits to demonstrating "how Dasher as a text entry system differs in text entry rates for users", both theoretically and empirically. This task designs an ethically reviewed study comparing current and novice Dasher users (application tasks 9 and 10), prepares participant materials, and obtains ethics approval. It then runs the study, measuring text-entry rates across access methods and prediction configurations, and publishes results and recommendations — including the optimal language-model and gRPC backend settings the scope document says "would need to be identified through this testing".

Suggested owners: WW, ANY

Milestone(s):
a. Study design, participant materials and ethics approval — €1,000
b. Study carried out with both existing and new Dasher users — €2,500
c. Public report with text-entry-rate results and recommended default settings — €1,000

Amount: €4,500

## Suggested owner split and geographic guardrail

Suggested (not binding) owner totals across the tasks above: WW €18,000 (36%), KM €23,000 (46%), UX €9,000 (18%). WW and KM are UK-based (a Horizon Europe associated country), so the named-owner baseline already directs €41,000 (82%) of the budget to Horizon-Europe-eligible contributors — comfortably above the 60% (€30,000) floor. The UX contributor will be recruited in a Horizon-Europe-eligible country where possible. Milestones not taken by the named owners are open to additional contributors, including non-European collaborators (for example US-based language-modelling expertise); the lead coordinates assignments so that combined payments to non-European contributors remain within €20,000, preserving the ≥60% Horizon-Europe share in all cases.

## Standing notes

- Milestones are payable at 100% completion of the task or subtask, on receipt of a Request for Payment; payments are donations, not contracts, and no VAT applies.
- The plan can be modified during the project in agreement with NLnet; tasks may be executed in any order.
- All tasks are research and development activities, including documentation and bug fixes. Operational costs, community management, hosting and promotional activities are not funded. Travel and hardware are not payable as milestones: where genuinely required for the R&D activities (e.g. participant travel for the user study), they must be agreed with NLnet in advance with invoices submitted ahead of any payment, and will be limited in scale.
- All work is publicly reviewable on github.com/dasher-project; progress is reported every two months alongside the public status page. These reporting obligations are conditions of the grant rather than funded tasks.

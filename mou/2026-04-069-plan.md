# Dasher v6 — Project Plan (Annex I to the MoU)

**Grant:** 2026-04-069 (NGI0 Commons Fund, April 2026 call)
**Project:** Dasher v6 — cross-platform, accessible continuous-gesture text entry
**Planned start:** October 2026
**Total budget:** €50,000

All work takes place in public in the [dasher-project](https://github.com/dasher-project) GitHub organisation. Tasks are executable in any order unless a dependency is stated; the plan can be modified in agreement with NLnet as the project evolves. Every task in this plan is a research and development activity — engineering, specification, bug fixing, evaluation or documentation.

**Owner initials:** WW (Will Wade, UK, project lead and point of contact), KM (Kirsty McNaught, UK, developer), UX (UX/design contributor, to be recruited), ANY (open to additional listed contributors). Owner assignment is flexible and coordinated with the lead; in this public document amounts attach to milestones, not to people.

## 1. Onboarding and first-run experience

Dasher's main adoption barrier, identified repeatedly in the project scope document and in community feedback, is that it is "a problematic interface to understand without training". This task delivers the start-up guide and first-run experience promised in the application and announced to the user community: user research with new and experienced Dasher users, wireframes, and a first-run flow that gets a new user writing quickly. Design work is captured in `dasher-design-guide` and implemented first in `dasher-web`, where iteration is fastest. UI strings and shared assets flow through `dasher-shared-resources` so all frontends present one consistent experience.

Suggested owners: KM, UX

Milestone(s):
a. User research round with new and existing Dasher users; findings and wireframes published in `dasher-design-guide` — €1,200
b. Start-up guide and first-run flow prototyped and implemented in `dasher-web` — €1,400
c. Onboarding experience integrated across the desktop and mobile frontends via `dasher-shared-resources` — €1,400

Amount: €4,000

## 2. Learning mode

Beyond the first run, new users need structured practice before continuous-gesture input feels natural. This task designs and delivers a learning mode replacing the legacy "game mode": graduated exercises that teach zoom dynamics, pointer control and word-building step by step, with progression that adapts as a user becomes proficient. The design is specified in `dasher-design-guide`, implemented first in `dasher-web`, and validated with genuine new users before shipping across the frontends.

Suggested owners: KM, UX

Milestone(s):
a. Learning-mode design and progression model specified in `dasher-design-guide` — €1,000
b. Learning mode implemented in `dasher-web` and one native frontend — €1,500
c. Progression tuned with new users and learning mode shipped across the frontends — €1,000

Amount: €3,500

## 3. Settings user experience

Dasher's power has historically been hidden behind a dense settings surface. This task overhauls the settings experience with progressive disclosure: the options a user actually needs first are discoverable and well-explained, while advanced and expert options remain reachable without overwhelming newcomers. The information architecture is designed once in `dasher-design-guide` and applied consistently across all platforms through `dasher-shared-resources`, with settings that carry over between the learning mode and normal use.

Suggested owners: KM, UX

Milestone(s):
a. Settings audit and progressive-disclosure information architecture published — €1,000
b. Overhauled settings implemented in `dasher-web` with inline explanation for key options — €1,200
c. Settings experience made consistent across the desktop and mobile frontends — €800

Amount: €3,000

## 4. Eye-gaze input performance

The scope document promises "a cross-platform, eye gaze, headmouse and direct accessible version of Dasher", and the user community has asked for eye-gaze to work really well. This task evaluates the current eye-gaze path end to end — pointer smoothing, zoom dynamics under continuous gaze, dwell behaviour and latency budgets — and specifies a calibration and profile workflow so a user's gaze setup survives restarts and moves between machines. Improvements land in `DasherCore` input filters (RFC 0010 canonical model) and are validated per platform against representative eye trackers.

Suggested owners: KM, WW

Milestone(s):
a. Eye-gaze input evaluation and calibration/profile specification published — €1,500
b. Tracking smoothing, zoom dynamics and latency improvements implemented in `DasherCore` input filters — €1,500
c. Per-platform eye-gaze validation with representative hardware, findings and default profiles published — €1,000

Amount: €4,000

## 5. Prediction engine: extending the RFC 0010 canonical model

The core of the application is "a new next letter and next n word prediction engine which will support a range of models in different languages". This task works with the RFC 0010 canonical model and extends it so prediction is pluggable behind a stable interface: offline models — a bundled default so Dasher works without any network connection, plus downloadable, cached models per platform — and, where they prove beneficial, online models served remotely behind the same interface with configuration discovery and graceful fallback. Emoji support requested by the user community is delivered here too: a settings-gated emoji group in the alphabet model, building on the open DasherCore#99 pull request. Keith Vertanen (language-modelling and text-entry research), KM and WW work together on this task.

Suggested owners: KM, KV, WW

Milestone(s):
a. Pluggable language-model interface specified and implemented in `DasherCore` under RFC 0010 — €2,000
b. Offline model support: bundled default model, packaging, download and caching across platforms — €2,500
c. Online model support where beneficial: remote models behind the same interface, configuration discovery, offline fallback — €1,500
d. Emoji support: settings-gated emoji group in the alphabet model, specified and shipped — €1,000

Amount: €7,000

## 6. Switch access: native operation and OS accessibility interoperability

Switch users are a core Dasher audience. This task takes a broad approach: switches working natively in the software — one-switch and two-switch scanning modes, timing and debouncing, and loadable switch profiles, specified through the switch-access RFC tracked as governance#43 — together with interoperability with operating-system accessibility frameworks where possible, so a user's existing platform switch setup (for example OS-level switch control events) can drive Dasher without bespoke configuration. Existing broker work (governance#25) may serve as one capture path where it fits. The goal: plug a switch into any supported platform and Dasher just works.

Suggested owners: KM, WW

Milestone(s):
a. Switch access profiles RFC written and accepted (closes governance#43): scanning modes, timing, hardware, profiles — €1,000
b. Native switch operation implemented in `DasherCore` and the desktop frontends — €2,000
c. Interoperability with OS accessibility frameworks where possible (platform switch/accessibility events feeding the engine) — €1,500
d. Loadable switch profiles, hardware notes and user documentation — €1,000

Amount: €5,500

## 7. Voice and speech output — scope under review (?)

> **Note: the shape of this task is genuinely unresolved.** It may turn out to be simpler than imagined — little more than unifying the existing per-platform TTS behind one consistent settings surface — or it may grow to include collaborative sprints with VoiceGarden. The milestones below are indicative; the task will be rescoped with NLnet once the approach is settled, within the €4,000 reservation shown (modifiable per the standing notes).

governance#42 records that speak-on-space, speak control nodes and per-platform TTS all exist in some form but without a specification — and that speech is "the voice of the product" for users who cannot look at the screen while typing. This task writes the voice/speech output RFC (when speech fires, interruption behaviour, voice selection, rate/volume/pitch ownership, direct-mode behaviour) and then unifies the existing per-platform implementations — speech-dispatcher via `tts-wrapper` (AACTools) on GTK, SAPI on Windows, Android TTS, AVSpeechSynthesizer on Apple — behind one consistent settings surface. It also hooks speech into the phrase/communication-board integration questions raised in the issue.

Suggested owners: WW, ANY

Milestone(s):
a. Voice/speech output RFC written and accepted (closes governance#42) — €800
b. Per-platform TTS unified behind consistent configuration across all frontends — €2,200
c. Speak-on-space and speak control node options exposed in settings, with documented behaviour in direct mode — €1,000

Amount: €4,000

## 8. Cross-platform parity: feature matrix, versioning, releases and stabilisation

The fragmentation of v5 across Windows, Linux, iOS and Android is the historical failure mode this project exists to fix. The standing question this task answers is: **how do we keep all platforms on feature parity?** That needs research first and then putting into place: a consistent versioning scheme across all the platform repositories (`Dasher-Android`, `Dasher-Apple`, `Dasher-GTK`, `Dasher-Windows`, `dasher-web`), linked to a feature matrix — or whatever equivalent mechanism the research lands on — so parity is visible, measurable and driven by CI against the governance#41 test checklist rather than assumed. On top of that: simultaneous tagged releases with notes, the application's deliverable 2 (on-screen keyboard integrations on iOS, Android and Windows so Dasher outputs text to the operating system), and the long-standing iOS and Android stability headaches the community has reported, fixed and verified against the checklist.

Suggested owners: KM, WW, ANY

Milestone(s):
a. Research report and accepted proposal: cross-repo versioning scheme linked to a feature matrix (or equivalent parity mechanism) — €1,000
b. Versioning and feature matrix implemented across the platform repositories, enforced by CI against the governance#41 checklist — €1,500
c. First simultaneous tagged release across all frontends with published release notes — €500
d. On-screen keyboard integration (OS text output) on iOS, Android and Windows — €2,000
e. iOS and Android stabilisation: crashers and long-standing platform bugs fixed, verified against the governance#41 checklist — €1,000

Amount: €6,000

## 9. Developer experience: documentation, examples and experiments

Dasher v6 succeeds if developers outside the core team can build with it. This task creates a first-class environment for users and developers: superb developer documentation covering architecture, building for each platform and the contribution path; worked examples for different use cases (embedding Dasher in an application, building alternative frontends); and published experiments for use cases that go beyond the C API layer — for example the 3D work, where a frontend consumes the engine through higher-level bindings rather than the C API. The outcome is a developer who goes from clone to a running, modified Dasher quickly, with clear paths for going further.

Suggested owners: KM, WW

Milestone(s):
a. Developer documentation overhaul: architecture guide, per-platform build instructions, contribution paths — €1,500
b. Worked examples for different use cases published (embedding, alternative frontends) — €1,500
c. Experiments with non-C-API paths (e.g. 3D work through higher-level bindings), published with findings — €1,500
d. First-class developer environment: templates and tooling so a new contributor goes clone-to-running quickly — €1,000

Amount: €5,500

## 10. User documentation and training videos

The application's deliverable 6 is "video content alongside a website to demonstrate Dasher's features for end-users and developers"; here it is scoped as documentation and training material. This task converts legacy word-processor documentation into markdown user guides hosted on the project `website` repository, covering installation, access methods, prediction settings and the new onboarding flow. It then produces short training videos for end users (getting started, switch access, voice output) and for developers (building the frontends), published alongside the written guides as training documentation.

Suggested owners: UX, WW, ANY

Milestone(s):
a. User guides published in markdown on the project website, produced with the UX team where possible — €1,200
b. End-user training videos (getting started, switch access, speech output) published, produced with the UX team where possible — €800
c. Developer-facing videos (per-platform builds) published — €1,000

Amount: €3,000

## 11. User research: empirical text-entry-rate evaluation

The application commits to demonstrating "how Dasher as a text entry system differs in text entry rates for users", both theoretically and empirically. WW and KM share this task. It designs an ethically reviewed study comparing current and novice Dasher users (application tasks 9 and 10), prepares participant materials, and obtains ethics approval. It then runs the study, measuring text-entry rates across access methods and prediction configurations, and publishes results and recommendations — including the optimal language-model and prediction settings the scope document says "would need to be identified through this testing".

Suggested owners: KM, WW

Milestone(s):
a. Study design, participant materials and ethics approval — €1,000
b. Study carried out with both existing and new Dasher users — €2,500
c. Public report with text-entry-rate results and recommended default settings — €1,000

Amount: €4,500

## Standing notes

- Milestones are payable at 100% completion of the task or subtask, on receipt of a Request for Payment; payments are donations, not contracts, and no VAT applies.
- The plan can be modified during the project in agreement with NLnet; tasks may be executed in any order.
- All tasks are research and development activities, including documentation and bug fixes. Operational costs, community management, hosting and promotional activities are not funded. Travel and hardware are not payable as milestones: where genuinely required for the R&D activities (e.g. participant travel for the user study), they must be agreed with NLnet in advance with invoices submitted ahead of any payment, and will be limited in scale.
- Generative AI use follows NLnet's policy, version 1.1 under the transitional arrangement for the NGI Zero Commons Fund: AI may assist development; generated code carries commit-level provenance marks; purely AI-generated outputs are not submitted as completed milestones. See the MoU clause 13.
- All work is publicly reviewable on github.com/dasher-project; progress is reported every two months alongside the public status page. These reporting obligations are conditions of the grant rather than funded tasks.
